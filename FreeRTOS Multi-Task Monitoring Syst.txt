2. WHAT IS AN RTOS?
Definition

RTOS stands for:

Real-Time Operating System

An RTOS is an operating system designed to manage multiple tasks where the timing of operations is important.

In embedded systems, different operations often need to happen at different time intervals.

For example, a train control system may need to:

Read sensors
Process communication
Monitor system health
Update a display
Handle alarms
Record diagnostic information

All these operations may need to happen independently.

An RTOS provides mechanisms to manage these operations.

Small Example

Imagine an embedded controller with three activities:

Task 1 → Read sensor every 100 ms

Task 2 → Send communication packet every 500 ms

Task 3 → Monitor system every 1 second

Without an RTOS, we may write one large loop:

while(1)
{
    ReadSensor();
    SendCommunication();
    MonitorSystem();
}

With an RTOS:

Sensor Task
Communication Task
Monitor Task

Each task can have its own timing and priority.

3. WHAT IS FREERTOS?
Definition

FreeRTOS is a real-time operating system kernel designed primarily for embedded systems and microcontrollers.

It provides facilities for:

Task management
Scheduling
Queues
Semaphores
Mutexes
Task notifications
Software timers
Memory management
Inter-task communication

FreeRTOS does not mean that it replaces all MCU firmware.

Instead:

Application
     ↓
FreeRTOS APIs
     ↓
FreeRTOS Kernel
     ↓
Hardware / MCU
Small Example

Without FreeRTOS:

while(1)
{
    Sensor();
    Communication();
    Display();
}

With FreeRTOS:

xTaskCreate(SensorTask, ...);
xTaskCreate(CommunicationTask, ...);
xTaskCreate(DisplayTask, ...);

vTaskStartScheduler();

The scheduler manages execution of the tasks.

13. WHAT IS FREERTOSCONFIG.H?
Definition

FreeRTOSConfig.h contains configuration options used to configure the FreeRTOS kernel for a particular application.

It determines things such as:

14. IMPORTANT FREERTOS CONFIGURATION

Example:

#define configUSE_PREEMPTION 1

This enables preemptive scheduling.

#define configTICK_RATE_HZ 1000

This configures a 1000 Hz RTOS tick.

That means approximately:

1 tick = 1 ms
#define configMAX_PRIORITIES 5

Defines the number of priority levels.

#define configTOTAL_HEAP_SIZE (64 * 1024)

Allocates 64 KB for FreeRTOS dynamic memory.

#define configUSE_MUTEXES 1

Enables mutex support.

#define configUSE_TIMERS 1

Enables software timers.

15. WHAT IS THE FREERTOS SCHEDULER?
Definition

The scheduler is the component of FreeRTOS responsible for deciding which task should execute.

For example:

Sensor Task       Priority 3
Communication     Priority 2
Monitor           Priority 1

If all are ready:

Sensor Task

gets CPU time first because it has the highest priority.

16. WHAT IS A TASK?
Definition

A task is an independent unit of execution managed by FreeRTOS.

You can think of a task as an independent function that has:

Its own stack
Its own execution state
Its own priority
Its own task control information
Small Example
void SensorTask(void *pvParameters)
{
    while(1)
    {
        printf("Reading sensor\n");

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

This task repeatedly reads a simulated sensor every second.

18. TASK FUNCTION

Every FreeRTOS task normally has this structure:

void TaskFunction(void *pvParameters)
{
    while(1)
    {
        // Task work
    }
}

The return type is:

void

The parameter is:

void *pvParameters

pvParameters allows us to pass information to a task when creating it.

Example:

int sensorID = 10;

xTaskCreate(
    SensorTask,
    "Sensor",

Inside the task:

void SensorTask(void *pvParameters)
{
    int id = *(int *)pvParameters;
}
20. TASK PRIORITY
Definition

Task priority determines the relative importance of tasks to the scheduler.

Example:

Sensor Task        Priority 3
Communication     Priority 2
Monitor            Priority 1

Higher number means higher priority in the normal FreeRTOS configuration.

Small Example

If:

Task A = Priority 3
Task B = Priority 1

and both are ready:

Task A

is selected first.

21. PREEMPTIVE SCHEDULING
Definition

Preemptive scheduling means the scheduler can interrupt a currently running lower-priority task when a higher-priority task becomes ready.

Example:

Low Priority Task
       ↓
Higher Priority Task becomes ready
       ↓
Scheduler
       ↓
Higher Priority Task runs

This is very important in real-time embedded systems.

22. FREERTOS TICK
Definition

The RTOS tick is a periodic interrupt/event used by the scheduler for timing and task management.

Our configuration:

#define configTICK_RATE_HZ 1000

Therefore:

1000 ticks / second

Approximately:

1 tick = 1 millisecond
23. vTaskDelay()
Definition

vTaskDelay() blocks the calling task for a specified number of RTOS ticks.

Example:

vTaskDelay(pdMS_TO_TICKS(1000));

This means approximately:

Sleep/block task for 1000 ms

During this time, another ready task can execute.

24. WHY USE pdMS_TO_TICKS()?

Instead of manually calculating ticks:

1000

we use:

pdMS_TO_TICKS(1000)

This makes the code easier to understand.

Example:

vTaskDelay(pdMS_TO_TICKS(500));

means:

Delay for approximately 500 ms
25. TASK STATES

A FreeRTOS task can be in different states.

Main states:

Running
Ready
Blocked
Suspended
Deleted
Running

Currently executing.

Ready

Ready to run but waiting for CPU time.

Blocked

Waiting for time or an event.

Example:

xQueueReceive(
    sensorQueue,
    &value,
    portMAX_DELAY
);

The task can become blocked waiting for queue data.

Suspended

Explicitly suspended.

Deleted

Task has been deleted.

Now:

sensorTaskHandle

It can be used for:

Notifications

27. QUEUE
Definition

A FreeRTOS queue is an inter-task communication mechanism used to transfer data between tasks.

Think of it as:

Task A
  |
  | Data
  ↓
[ QUEUE ]
  |
  | Data
  ↓
Task B
28. SMALL QUEUE EXAMPLE

Create queue:

QueueHandle_t sensorQueue;

sensorQueue = xQueueCreate(5, sizeof(int));

This means:

Queue length = 5
Each element = sizeof(int)

Send data:

int value = 25;

xQueueSend(
    sensorQueue,
    &value,
    portMAX_DELAY
);

Receive:

int receivedValue;

xQueueReceive(
    sensorQueue,
    &receivedValue,
    portMAX_DELAY
);
29. PRODUCER-CONSUMER CONCEPT

The task sending data is called the:

Producer

The task receiving data is called the:

Consumer

Our project:

Sensor Task
    |
    | produces sensor data
    ↓
Sensor Queue
    |
    | consumes sensor data
    ↓
Communication Task

This is a classic RTOS producer-consumer architecture.

30. WHY USE A QUEUE?

Without a queue:

Sensor Task
     ↓
Global variable
     ↓
Communication Task

This can introduce synchronization problems.

With a queue:

Sensor Task
     ↓
Queue
     ↓
Communication Task

FreeRTOS handles the synchronization associated with queue access.

31. BINARY SEMAPHORE
Definition

A binary semaphore is a synchronization mechanism with two logical states:

Available
Not available

It is commonly used for signaling an event.

32. SMALL BINARY SEMAPHORE EXAMPLE

Create:

SemaphoreHandle_t eventSemaphore;

eventSemaphore = xSemaphoreCreateBinary();

Give:

xSemaphoreGive(eventSemaphore);

Take:

xSemaphoreTake(
    eventSemaphore,
    portMAX_DELAY
);
33. BINARY SEMAPHORE IN OUR PROJECT

The Sensor Task gives the semaphore:

xSemaphoreGive(eventSemaphore);

The Communication Task waits:

xSemaphoreTake(
    eventSemaphore,
    portMAX_DELAY
);

Conceptually:

Sensor Task
    |
    | Event happened
    ↓
Binary Semaphore
    |
    ↓
Communication Task
34. QUEUE VS BINARY SEMAPHORE
Queue	Binary Semaphore
Transfers data	Signals event
Stores values	Usually stores only availability state
Producer/consumer	Synchronization
Example: sensor value	Example: event occurred

Interview answer:

A queue is primarily used to transfer data between tasks, while a binary semaphore is primarily used for synchronization or event signaling.

35. MUTEX
Definition

Mutex stands for:

Mutual Exclusion

A mutex is used to protect a shared resource from simultaneous access by multiple tasks.

36. SHARED RESOURCE

Suppose two tasks execute:

printf("Hello");

at the same time.

The console is a shared resource.

We can protect it:

Task A
   |
   | Take Mutex
   ↓
[ Shared Resource ]
   |
   | Give Mutex
   ↓
Task B
37. MUTEX EXAMPLE

Create:

printMutex = xSemaphoreCreateMutex();

Take:

xSemaphoreTake(
    printMutex,
    portMAX_DELAY
);

Access resource:

printf("Sensor data\n");

Release:

xSemaphoreGive(printMutex);
38. MUTEX IN OUR PROJECT

We created:

static SemaphoreHandle_t printMutex;

Then:

printMutex = xSemaphoreCreateMutex();

We created a helper:

SafePrint()

which takes the mutex before calling printf().

Concept:

Sensor Task
       \
        \
Communication Task → Mutex → printf()
        /
       /
Monitor Task

Only one task should access the protected logging resource at a time.

39. MUTEX VS BINARY SEMAPHORE

This is an important interview question.

Mutex	Binary Semaphore
Protects shared resource	Signals event
Has ownership concept	No ownership concept
Supports priority inheritance	Mutex supports priority inheritance
Used for mutual exclusion	Used for synchronization
Example: shared UART/log	Example: interrupt event
40. PRIORITY INHERITANCE
Definition

Priority inheritance is a mechanism associated with FreeRTOS mutexes that helps reduce priority inversion.

Example:

Low Priority Task
      |
      | owns mutex
      ↓
   Mutex

High Priority Task
      |
      | needs mutex
      ↓
   Blocked

A medium-priority task could otherwise interfere.

Priority inheritance allows the lower-priority mutex holder to temporarily inherit the higher priority.

Interview statement:

FreeRTOS mutexes support priority inheritance to help mitigate priority inversion.

41. TASK NOTIFICATION
Definition

Task notifications are a lightweight mechanism for sending an event or small amount of information directly to a task.

They are often faster and use less memory than creating a separate queue/semaphore object for simple task-to-task signaling.

42. SMALL TASK NOTIFICATION EXAMPLE

Notify:

xTaskNotifyGive(taskHandle);

Wait:

ulTaskNotifyTake(
    pdTRUE,
    portMAX_DELAY
);

Concept:

Task A
  |
  | Notify
  ↓
Task B
43. TASK NOTIFICATION IN OUR PROJECT

The Sensor Task sends:

xTaskNotifyGive(
    communicationTaskHandle
);

The Communication Task waits:

ulTaskNotifyTake(
    pdTRUE,
    portMAX_DELAY
);

Therefore:

Sensor Task
    |
    | Task Notification
    ↓
Communication Task
44. QUEUE VS NOTIFICATION
Queue	Task Notification
Can transfer data	Directly signals a task
Queue object required	Uses task's notification state
Multiple data elements possible	Lightweight
Producer-consumer	Event/task signaling
More general	Very efficient for simple signaling

Interview statement:

Task notifications are lightweight direct-to-task signaling mechanisms and are useful when a full queue or semaphore is unnecessary.

45. SOFTWARE TIMER
Definition

A software timer is a FreeRTOS mechanism that executes a callback function after a configured period.

It does not require creating a dedicated application task for every timer.

46. SMALL TIMER EXAMPLE

Create:

TimerHandle_t systemTimer;

systemTimer = xTimerCreate(
    "SystemTimer",
    pdMS_TO_TICKS(5000),
    pdTRUE,
    NULL,
    SystemTimerCallback
);

Start:

xTimerStart(
    systemTimer,
    0
);

Callback:

void SystemTimerCallback(TimerHandle_t timer)
{
    printf("Timer expired\n");
}
47. TIMER PERIOD

Our timer period:

#define TIMER_PERIOD_MS 5000

Therefore:

5 seconds

The timer repeatedly generates the callback.

48. AUTO-RELOAD TIMER

The timer uses:

pdTRUE

for the auto-reload parameter.

Therefore:

5 sec
 ↓
Callback
 ↓
5 sec
 ↓
Callback
 ↓
5 sec
 ↓
Callback

If:

pdFALSE

is used, the timer becomes a one-shot timer.

49. TIMER CALLBACK

A timer callback is a function called by the FreeRTOS timer service when the timer expires.

Example:

static void SystemTimerCallback(TimerHandle_t timer)
{
    printf("[TIMER] Software Timer expired.\n");
}

Important:

A software timer callback executes in the FreeRTOS timer service task, not in the context of the task that created the timer.

50. TASK MONITORING
Definition

Task monitoring means checking the condition and resource usage of RTOS tasks during execution.

This helps identify:

Blocked tasks
Unexpected task states
Stack problems
Task failures
System health issues
51. eTaskGetState()

We use:

eTaskGetState(taskHandle)

to obtain a task's current state.

Example:

eTaskState state;

state = eTaskGetState(sensorTaskHandle);

The result can represent states such as:

Running
Ready
Blocked
Suspended
Deleted

Do not rely on raw numeric enum values such as 2; use the symbolic FreeRTOS states when interpreting results.

52. STACK MONITORING
Definition

Every FreeRTOS task has a stack.

The stack stores information needed during task execution.

If a task uses more stack than allocated, stack overflow can occur.

This can cause:

Memory corruption
Crashes
Unexpected behavior
Hard-to-debug failures
53. STACK SIZE

When creating the task:

xTaskCreate(
    SensorTask,
    "Sensor",
    1024,
    NULL,
    3,
    &sensorTaskHandle
);

The 1024 parameter represents the stack depth in units defined by the FreeRTOS port.

It should not automatically be interpreted as 1024 bytes on every architecture.

54. uxTaskGetStackHighWaterMark()
Definition

uxTaskGetStackHighWaterMark() reports the minimum amount of stack space that remained unused for a task since the task started.

Example:

UBaseType_t remaining;

remaining =
    uxTaskGetStackHighWaterMark(
        sensorTaskHandle
    );

If the value becomes very small, the task may need more stack.

55. HIGH-WATER MARK EXAMPLE

Suppose:

Allocated stack = 1024 units
Minimum unused = 100 units

That means the task came close to using the available stack.

If:

Minimum unused = 10

we should investigate whether the stack allocation is sufficient.

56. INTERRUPT
Definition

An interrupt is a hardware-generated event that temporarily interrupts normal CPU execution so that an urgent event can be handled.

Examples:

GPIO button press
UART receive
Timer interrupt
ADC conversion complete
CAN message received
57. NORMAL INTERRUPT FLOW

58. WHAT IS AN ISR?

ISR means:

Interrupt Service Routine

It is the function executed in response to an interrupt.

Example STM32-style callback:

void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    // Handle GPIO interrupt
}
59. ISR-TO-TASK COMMUNICATION

An ISR should normally perform minimal work.

Instead of doing heavy processing:

ISR
 ↓
Signal task
 ↓
Task performs processing

For example:

GPIO interrupt
      ↓
ISR
      ↓
Task notification
      ↓
Event Task
      ↓
Process event
60. FromISR APIS

FreeRTOS provides APIs specifically designed for interrupt context.

Examples:

xQueueSendFromISR()
xSemaphoreGiveFromISR()

These are different from normal task-context APIs.

61. SIMULATED INTERRUPT IN OUR PROJECT

97. INTERVIEW QUESTION — WHAT IS FREERTOS?

Answer:

FreeRTOS is a real-time operating system kernel for embedded systems. It provides task scheduling, inter-task communication, synchronization mechanisms such as queues, semaphores and mutexes, task notifications, software timers, and memory management.

98. INTERVIEW QUESTION — WHAT IS A TASK?

Answer:

A task is an independent unit of execution managed by the FreeRTOS scheduler. Each task has its own stack, priority, state, and task control information.

99. INTERVIEW QUESTION — WHAT IS A QUEUE?

Answer:

A FreeRTOS queue is an inter-task communication mechanism used to safely transfer data between tasks. It is commonly used in producer-consumer architectures.

100. INTERVIEW QUESTION — QUEUE VS SEMAPHORE?

Answer:

A queue is mainly used for transferring data, while a semaphore is mainly used for synchronization or event signaling.

101. INTERVIEW QUESTION — WHAT IS A MUTEX?

Answer:

A mutex provides mutual exclusion when multiple tasks access a shared resource. Only one task can own the mutex at a time.

102. INTERVIEW QUESTION — MUTEX VS BINARY SEMAPHORE?

Answer:

A mutex is primarily used to protect a shared resource and has ownership semantics with priority inheritance. A binary semaphore is primarily used for synchronization or event signaling and does not have the same ownership semantics.

103. INTERVIEW QUESTION — WHAT IS PRIORITY INHERITANCE?

Answer:

Priority inheritance is a mechanism used with mutexes to reduce priority inversion. When a high-priority task is blocked by a lower-priority task holding a mutex, the lower-priority task can temporarily inherit the higher priority so it can release the mutex sooner.

104. INTERVIEW QUESTION — WHAT IS TASK NOTIFICATION?

Answer:

A task notification is a lightweight direct-to-task signaling mechanism. It is useful when a task needs to be notified about an event without creating a separate queue or semaphore object.

105. INTERVIEW QUESTION — WHAT IS A SOFTWARE TIMER?

Answer:

A FreeRTOS software timer allows a callback function to be executed after a configured period. A timer can be one-shot or auto-reloading.

106. INTERVIEW QUESTION — WHAT IS STACK OVERFLOW?

Answer:

Stack overflow occurs when a task requires more stack space than was allocated to it. It can cause memory corruption and unpredictable behavior, so task stack usage should be monitored and configured appropriately.

107. INTERVIEW QUESTION — WHAT IS STACK HIGH-WATER MARK?

Answer:

The stack high-water mark indicates the minimum amount of unused stack space observed for a task since the task started. It helps determine whether the allocated task stack is sufficient.

108. INTERVIEW QUESTION — WHAT IS ISR?

Answer:

ISR stands for Interrupt Service Routine. It is executed when a hardware interrupt occurs. In an RTOS system, the ISR should normally perform minimal work and signal a task to perform the larger processing operation.

109. INTERVIEW QUESTION — WHY USE FromISR API?

Answer:

FreeRTOS provides special FromISR APIs because interrupt context has different execution requirements from normal task context. For example, vTaskNotifyGiveFromISR() can notify a task safely from an ISR.

110. INTERVIEW QUESTION — WHY DID YOU SIMULATE INTERRUPTS?

Answer:

I initially developed the project on Windows because the STM32 hardware was not available. Therefore, I simulated the interrupt event using a task and task notification. The architecture is designed so that it can later be connected to a real STM32 ISR using the appropriate FromISR API.

111. INTERVIEW QUESTION — WHY USE TASK HANDLES?

Answer:

Task handles provide references to specific tasks. They can be used for operations such as notifications, monitoring, state checking, suspension, and resumption.

112. INTERVIEW QUESTION — WHY USE A MUTEX FOR PRINTF?

Answer:

In the Windows simulation, the console output is treated as a shared resource. Multiple tasks can print messages, so I use a mutex to serialize access to the logging function. On the actual embedded target, the same concept could be applied to shared UART or another common peripheral resource.
